# T128 · What the external renderer actually does

**Frame 145 is already live.** At the pinned Blackbody revision `e2ac951dbfabc6060073943e4c344439ac5f4555` (package 1.0.0), `simulate_to(scene,145,cache=False)` advances the physical solver and sets the current frame. The fire renderer then takes pointers to that frame's live scalar, velocity and cloth buffers. It neither restarts nor advances the gas or cloth. A request for an unavailable, non-live frame raises an error; the render function will not simulate its way there. The former T126 worker reached this stage at 88.55 s, and its host stopped it at 240.22 s. Its last marker precedes *both* image renders and their readbacks. Which call occupied the remaining interval is unknown. T128 parsed source without running a GPU, scene, solver, renderer, or performance trial. ### What precedes the first pixel

1. The renderer resolves the frame's camera, look, compositing settings, scene colliders, holdouts and simulation time. Depending on current settings and prior use, preparation can upload lookup tables and create GPU buffers. The curtain uses its live vertex coordinates when `sim_frame == frame`. With cloth present, `prepare_light` can allocate an occlusion buffer in advance of the first render batch. [Frame setup](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/engine.py#L818-L875) · [Cloth occlusion allocation](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/cloth.py#L1087-L1095)
2. The first top-level operation recorded inside this batch is `Renderer.light`. It prepares the blackbody colour response and light-volume textures; its first ordinary compute dispatch is `k_emit`, a *volume lighting* source. Cloth occlusion then splats into the light grid, followed by other light extraction, blur and shadow work. This happens before the camera ray march and before the screen-space target can exist. The source order identifies dependencies; it supplies no time breakdown. [First dispatch and lighting](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/renderer.py#L550-L605) · [Occlusion writes](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/cloth.py#L1096-L1113)
3. The fixed single-sample path optionally draws the stage, rasterizes the fabric to bound the camera ray, marches the volume, merges surfaces, draws eligible embers, applies defocus/bloom and composites into output textures. Native pipelines can be created lazily. Encoding or submitting those GPU commands is distinct from observing finished pixels. A queue completion or synchronizing texture read provides an explicit timing boundary. [Single-sample path](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/engine.py#L876-L900) · [Embers and compositing](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/engine.py#L926-L934) · [Native submit](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/gpu.py#L681-L690) · [Texture readback](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/gpu.py#L1113-L1122)

### One render answers the primary question

T124 defined its primary endpoint on the native **fire-element emission texture**. After its ordinary `mode='fire'` render, `engine.gpu.read(engine.renderer.emit)` reads the very texture that `Engine.aovs()['emission']` returns. This skips transfers of beauty, auxiliary, surface, mask, lamp and fabric buffers that the primary decision does not use. `aovs()` alone cannot generate an image from an unrendered physics state. The emission array, integer count and threshold decision can be durably saved before asking for any context image. [Explicit AOV mapping](https://github.com/gjnail/blackbody/blob/e2ac951dbfabc6060073943e4c344439ac5f4555/blackbody/engine/engine.py#L1071-L1086)

The separate T124 context output is the scene-linear **composite**. A fire-mode call followed by `linear_comp()` returns its fire-mode composition; the native export path separately requests composite mode for the fully staged image. Conversely, a composite call also produces an emission texture and a linear composite, making it a conceivable one-call shortcut. Stage selection depends on render mode, and stage depth can change ray termination. This shortcut requires same-live-frame comparison against the frozen fire element, including the emission array/crop, choice and composite. No such comparison has occurred. For an identical primary result today, use the fire render; to retain the original two-product contract, subsequently run the ordinary composite render. A fresh-process *simulation continuation* carries an additional risk. `Cloth.save_state/load_state` handles the vertex arrays but omits the cloth-to-gas grid `G` and its `_couple_filled` flag. Reset/allocation clears this flag. The next solver substep calls the cloth feedback hook before the fabric steps and splats a new grid; the hook exits on an unfilled grid. A resumed run can consequently omit feedback for a first substep if that grid is missing and would have been nonempty. No discrepancy was numerically measured here. Rerendering a saved frame without advancing it and continuing physical simulation have different verification requirements. ### Frozen diagnostic interface for a future run

The Python helper's only command line mode reads the pinned source AST and verifies direct native calls. Run `python render_probe.py --check-source PATH_TO_CHECKOUT` to repeat that check without importing Blackbody or requesting an adapter. A separately authorized observer can call `capture_endpoint(engine, scene, FRESH_DIRECTORY)` on an existing live or cached frame. It logs and flushes host entry/return for the render, light setup, cloth raster, camera march, native compilation notifications, queue fence and each required readback. Native `on_compile` issues a pre-compilation notification on some compute-kernel cache misses; it does not cover every graphics pipeline. The helper atomically saves the original emission plane and score before it attempts to render the context composite. Diagnostic logging, queue fences and disk I/O affect latency, and the helper has only been syntax/source-checked. [Source-only check and diagnostic adapter](render_probe.py)

For a future cache qualification, save the original project and one native frame entry **while frame 145 is still live**, before making the first renderer call. A compact normal path is `entry=engine.snapshot(scene)` followed by the native `write_entry` and `read_entry` on a fresh file. Verify readback, array dtypes/shapes/digests and the presence of cloth positions/state. In a fresh process prepare that same project, insert the verified entry with `engine.cache.put(145, entry)`, ensure `sim_frame != 145`, then render frame 145 without advancing. Measure save/read/configuration costs, compare against the original live element and composite, and report any pixel/decision differences. For true continuation, add a separate full-checkpoint + one-physical-step test that includes gas, material and folded-in cloth source fields. No rendering, replay or checkpoint was performed for T128.
