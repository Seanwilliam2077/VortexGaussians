# T129 · A second camera makes physical transport useful for a visible-gas editing decision

For camera 0, a native displayed-gas query accepts the lighter woodpile brush. When the editor also asks about camera 124, the light brush fails that view. Its heavier alternative must be evaluated and also fails. The two algorithms returned the same changed shell masses and camera choices for all 56 issued actions. Under the joint request, transferring the full physical state from the light brush's certified 24-step checkpoint reduced the heavier candidate's remaining work from 90 to 66 steps. All 12 paired measured joint calls favored transport, with a 9.1% lower per-process median in each fresh browser. For camera 0 alone the heavier branch was never required, zero steps were reused and the ordering varied. All medians use the six measured actions within each process and scope. Each warmup separately cleared the immutable donor/recipient caches. Both methods use the same cold-only heat index, cached donor graph, final renderer, depth compositing, crop for GPU readback and exact pixel test. A camera that accepts light skips its full-brush render. For the joint action, both draw and read back six frames in total: three required candidate/camera combinations, each with a full render and same-state gas-suppressed control. The median cost of these six draws/readbacks was 66.6–67.3 ms in both processes across both methods. Relative to ordinary, transport's physics phase dropped from 841.7 to 758.5 ms in process 1 and from 866.2 to 783.4 ms in process 2. Each captured trial includes fork/restore, the brush footprint, speculative checkpoint where applicable, physics, native rendering/readback, comparison and delivery back to the host. Rendered results, checkpoint states and answers were fresh for each action. The stable donor and projection tables were reused.

Producing and validating the two fixed opacity tables took 2,034 ms from host process launch to exit, including 1,865 ms inside the packager. The tables contain 1,985,280 bytes. Reading and installing both took another 39.0 and 39.6 ms across processes. These shared setup costs apply to either solver when starting from unprepared camera maps. The bundle is prepared for both registered views even in the subsequent single-view measurement. Setting up the live editor (browser launch, geometry loading, first stroke and stepping to its common pre-click parent) has separate timings in each process receipt. The bounds for final readback cover 76×80 native pixels for camera 0 and 146×162 for camera 124; the native renderer still draws the 940×528 viewport. The separate correctness audits matched the direct native T127 endpoint state for each brush, all eight original full-image PNG digests at +90 for each method, and both camera readouts including the skipped full-brush camera 0 image. They ran outside delivered-action timings. This experiment uses one known, investigator-specified woodpile edit with two calibrated views, a fixed numerical gas-display threshold and a single host. It tests a specific compositing decision. Independent simulations, human application and other high-performance native GPU reductions or renderers remain open.

## Reproduce

Run `python verify_results.py` from this directory to recompute all decisions, matched phase medians, win counts and process ratios against the public T127 receipts with Python's standard library. To rerun native execution, stage the [Firewoods inputs](../t127-woodpile-native-camera/README.md), set `FIREWOODS_SOURCE` to that input directory and optionally `BROWSER_EXECUTABLE`, `PLAYWRIGHT_MODULE` and `T129_PYTHON`. Run `node run.mjs FRESH_OUTPUT_DIRECTORY` and then `python verify_results.py --evidence FRESH_OUTPUT_DIRECTORY`. Weight generation needs NumPy and Pillow. The driver reconstructs the fixed two-view maps in a temporary directory, runs the serial browser blocks, and saves compact receipts. Fitted color images stay private.
