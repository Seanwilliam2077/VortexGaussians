# Does demand for individual emitter IDs avoid reconstructing 72 material steps?

It saves four on the expensive B→A camera-matte query. The ordinary active solver took 588.4 ms and eager material repair took 679.7 ms, including 155.0 ms of material reconstruction. Postponing that work until each successive emitter rank is required still requests **68 of the 72 chronological material scans** before returning the same quarter-matte milestone. The registered 80% rejection gate fired at 94.4%. This rejects this particular way of avoiding the B→A repair cost; it leaves open faster ways to evaluate each material update. Each row stops before the returned milestone's feed. The candidate receives the ordered frontier and emission cursor at the clicked cut. It may read prior gas-driven material onset batches chronologically up to the current scan only. The offline screen substitutes the native onset list for actually paying to reconstruct each such batch. It therefore counts the ideal replay demand of this algorithm; the study ran no simulator or latency benchmark. SHA-256 inputs match the public T108 captures. Every individual offered ID and final per-frame cursor agreed with the independent full-ledger walk. Archived full material/frontier/cursor snapshots agreed where available. The elapsed binary32 fuel lower bounds at the target were 0.378 for A→B and 0.261 for B→A, so the ordered frontier only appends in either interval.

B→A starts from 4,399 burners and cursor 939. At frame 253, the next 48 offers extend beyond the known tail. To resolve them, replay from frame 181 through 219. Later services keep asking for successively deeper ranks. At frame 264, zero-based slot 18 actually emits from rank 4,942, material ID 378, which first ignited at frame 247. Even an oracle that reveals all real cursors and skips every rejected service needs *at least* the first 67 material scans if it discovers that ID by sequential material reconstruction. The all-offer implementation consumes 68, retaining up to 73 historical deposition frames (373,760 bytes using T100's fixed-capacity sample arrays, plus other state). Among the 2,040 births, 311 were sourced from sites appended after the click.

A→B also exposes a counterexample to a guessed modulo. At frame 213, B→A's no-wrap pattern no longer applies: A→B actually wraps at zero-based slot 22 at length 3,740. There could be more newly appended sites until the current scan is known, so using the old queue length there would change the addressed source. Resolving the true length takes all historical scans through frame 213, one more than eager repair's two completed blocks. The B→A sequence has no actual wrap through the return, despite exhausting the initially *known* queue tail.

For global post-click admission, all nine layers have VIC storage, the VPM path injects no grid heat and the gas emitter and embers are disabled. Each nonfull offer consumes one coin; success consumes five additional random values. Global fullness is then checked again at the next offer. The oracle regenerates these coins at their recorded mulberry32 draw positions, infers pre-feed occupancy, and validates final occupancy and total draws. It grants the exact wrap history for free and drops the need to know nonbirth IDs. Its lower bound applies to the specified family of prefix-materializing algorithms. It does not establish a general lower bound on independent site evaluation or an arbitrary exact rank query.
