# Can demand for newly appended emitter ranks lag behind the current material time?

T108 Firewoods B→A's quarter-matte query is known to end at +86 and reconstruct 72 complete material steps, which cost about 155 ms. A→B ends at +44 with 32 reconstructed steps. Use these two registered, known T108 inputs, without choosing an alternative expiry or target. The proposed mechanism maintains a second chronological *material-only* replay cursor. It recovers the previously unknown appended emitter IDs only when the current feed services require more ranks than are already known. Gas, RNG and the projected material remain at the current simulated frame. The retrospective material state may lag many frames behind them.

In the capped native setup the initial graph donor prefix remains constant as long as all old burners survive and its cap is already saturated. Assume positive fuel throughout the query for each old burner, verify it from the cut, and verify enough lifetime for newly appended burners. These are controls for the method, not retrospective assumptions to silently infer from future events. Feed and graph donor order are different. Initial emission length and cursor come from the exact post-click state. Every historical complete/material-only update reads just earlier, already observed native-order gas deposits and the original deterministic material update. A single material step exposes the complete new-ignition ID batch in ascending scan order. Keep every recovered batch. A service starting at cursor c and needing b offers has an exact no-wrap certificate if the known ordered frontier length exceeds c+b. If shorter, advance retrospective replay one historical material scan at a time, never beyond the current scan, until the certificate holds or the actual current total is known. In the latter case, execute the native modulo with the exact current length, including any wrap. This conservative test demands every offered rank and makes no claims about the unknown source of a rejected coin or the effect of an unknown modulo.

First perform an offline *best-case material-step demand screen* on the two full, already published T108/T86 traces. Use the frozen algorithm above with sequential access to past per-frame appends as a stand-in for actual costly replay. A scorer with separate access to complete native histories computes every offered ID and cursor, checks the native stored cursor at available cuts, and matches the candidate at each service. No event rows may be read beyond the present scan; report deepest retrospective age, first expiry, total material steps, peak newly recovered IDs, checkpoints, actual wrap counts and numerical fuel guard. Distinguish replay of stored native labels in this opportunity screen from an implemented answer operator. The existing eager repair and ordinary full material are the cost controls. Also calculate an oracle lower bound on historical scans required by a scheme that still materializes the exact entire ordered prefix before actual native successful births, ONLY when acceptance and cursor trajectory can be independently determined from trace fields; report unavailable fields explicitly.

If even this free-label, incrementally amortized screen needs >=80% of T108's 72 B→A repair steps by the true target, stop before native implementation. It would remove too little chronological work to explain T108's 91 ms loss against ordinary. If <=50% is sufficient on B→A, qualify the mechanism for separate native code and end-to-end timing; 50–80% is inconclusive. A→B supplies a secondary transfer check without overriding the primary gate. Explicitly keep same-step wrap cases, cache and retained hot-log cost. Never transplant the next oracle event/accepted emitter into a real simulator. The access/cost accounting is independent of the number of material sites sampled by a spatial alternative.
